# 推理服务：负载分布、动态批处理和有效吞吐

> 日期：2026-11-25。性质：`derived` 条件关系与 `hypothesis` 建模方案；算例为合成数据。没有经过校准的通用尾延迟预测器。

服务效率取决于请求如何共同使用资源。同一个更快的 kernel，在低负载下可能降低响应时间，在接近容量时可能显著减少排队，在另一种请求分布下则可能没有价值。服务层把局部工作效率转化为用户实际得到的速度与完成率。

## 1. 工作负载是联合分布

至少需要描述到达间隔、输入长度、实际输出长度、前缀复用、采样/终止规则及不同请求类型的关联。用几个平均值替代整个分布可能丢掉决定成本的量。

**合成例：** 一组请求全部为 5000 个输入 token；另一组各有一半为 1000 和 9000。平均长度都为 5000，但平方均值分别为 $25\times10^6$ 与 $41\times10^6$。在只比较长序列因果全注意力的二次项时，后一组的该项平均工作约为前者的 1.64 倍；线性投影成本、状态共享和真实执行效率另计。这不是两组实际 TTFT 的倍数。

平均长度相同也不意味着尾部相同。长请求是否集中到达、是否共享前缀、是否对应更长输出，都会改变状态峰值和排队。用于复现的 trace 应保留这些依赖，脱敏可以替换内容或键，但应说明哪些结构仍被保留。

## 2. 动态 batch 是状态相关的服务过程

一次调度可写成条件成本函数：

$$
T_{\rm step}=g(B_d,N_p,\{\ell_i\},\text{cache},\text{routing},\text{backend}),
$$

其中 $B_d$ 为 Decode 请求数，$N_p$ 为本步 Prefill token 数。步骤完成后，输出、剩余输入、状态容量和队列共同更新。混合执行改变形状和共享，因此 $g$ 一般不等于纯 Prefill 与纯 Decode 耗时直接相加。

Chunked Prefill 用执行粒度调节长 Prefill 对 Decode 的影响；Sarathi-Serve 是这一方向的代表研究。[1] chunk 更小可能减少单次阻塞，同时增加调度、重复执行或效率损失，故不存在脱离负载和 SLO 的统一最优 chunk。

Little 定律 $\mathbb E[N]=\lambda\mathbb E[T]$ 要求稳定系统及匹配的计量边界。$N$ 包含等待、活跃和可能暂停的请求，不能直接当作 GPU 上的活跃 batch。M/M/1 等简单队列可以解释接近容量时等待放大，但其固定服务率、到达与服务假设不自动适用于 LLM 动态 batch，更不能直接据此输出 p99。

## 3. 把三种“吞吐”分开

| 量 | 所回答的问题 | 关键条件 |
| --- | --- | --- |
| 固定 offered load 的完成吞吐 | 当前流量完成了多少 | 实际发送速率、失败及观测窗口 |
| 饱和处理容量 | 资源最多能持续完成多少 | 稳定负载、队列不持续发散 |
| SLO goodput | 有多少请求同时正确完成且满足服务要求 | 固定质量与全部延迟约束 |

稳定、无丢弃时，完成请求速率等于接纳率。把处理容量从 100 提升到 120 requests/s，并不会在每秒仅到达 20 个请求时凭空增加完成吞吐；收益可能体现为延迟、余量或更少资源。

对同一个测量集合，直接定义：

$$
G=\frac{\sum_i\mathbf1\{\text{success}_i\land\text{quality}_i
\land\text{TTFT}_i\le s_F\land\text{TPOT}_i\le s_D\}}{\Delta t}.
$$

是否适用 TPOT 以及输出不超过一个 token 时的规则应预先约定。不能把 TTFT、TPOT 的边际合格率直接相乘。**合成例：** 假设全部请求正确完成，两项达标率各为 90%，联合达标率只能确定在 80%–90% 之间，未必是 81%。这是事件交集的上下界，不是独立性假设。

## 4. P/D 分离改变资源匹配，也增加状态传输

当 Prefill、Decode、状态传输均按同一工作负载折算成 requests/s 时：

$$
\lambda_{\rm sustainable}\le
\min(n_P\mu_P,n_D\mu_D,\mu_{\rm transfer}).
$$

固定总卡数要求 $n_Pg_P+n_Dg_D=G_{\rm GPU}$，另核对拓扑及实际分配。上式是必要容量筛选，未包含排队、突发和尾部，也不保证 SLO。传输需覆盖恢复推理所必需的全部状态，而非默认只有普通 KV。

DistServe 研究了阶段分离、各阶段资源/并行度与网络带宽的联合选择。[2] 本仓库借鉴其问题分解，具体硬件及引擎上的收益需要单独验证。共置可能在低负载下更简洁；分离可能通过减轻干扰改善高负载 SLO，但负载失衡与传输可以抵消收益。

## 5. 什么证据能支持尾延迟结论

开环实验固定计划到达轨迹，并记录计划与实际发送的偏差；客户端限流会掩盖服务端压力。闭环固定并发，完成后补请求，其输入率由系统反过来决定，不能把两种负载模式的数字混为同一容量。

分位数应从每请求/每 token 时间线统计，不能将各阶段 p95 相加；失败、超时、取消和排空不能选择性排除。相邻请求可能共享一个 batch、缓存或突发，因此不确定性估计应保留这些相关结构。样本不足时报告局限，而不是给稳定的 p99 小数。

真实动态服务预测需要经过独立校准的步骤成本、调度状态和事件回放。Vidur 将 profiling、算子预测与服务仿真相结合，可作为方法参考；它的已发表精度不代表本仓库已有相同能力。[3]

**可证伪预测：** 固定输入轨迹与资源后，某候选若被预测提升 SLO goodput，就必须在联合达标计数中体现；仅平均 kernel 时间下降而队列、错误率或尾延迟恶化，不支持这项服务结论。

Agent 选择策略时应以预先固定的服务目标为依据，记录负载适用域和回归场景。模型见[性能模型](../../models/README.md)，优化见[自主优化](../../optimizer/README.md)，执行规则见[实验平台](https://github.com/Sunhuahai/llm-inference-theory/blob/1b4c5a37763475eb39b31dd083fcad256fc2578e/experiments/README.md)与[测量协议](../../docs/benchmark-protocol.md)。
