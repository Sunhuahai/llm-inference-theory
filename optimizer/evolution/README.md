# 代码与配置的持续演化

> 状态：实施设计。这里研究如何积累可验证改动；目前没有自动生成或合并补丁的已实现系统。

## 1. 保存完整实现，再比较修改

一个实验结果属于“基线代码 + 候选补丁 + 配置 + 环境 + 工作负载”的组合。单独保存一段快 Kernel 无法判断它是否能在目标引擎正确工作。

最少保留四类引用：固定原始基线、当前确认最优、正在评估的候选、失败候选。最近一次修改不自动成为当前最优。Git worktree 能从同一仓库建立多个工作目录，可作为候选隔离的工程工具；它不会自动隔离 GPU、端口或全局缓存，后者仍需控制器管理。[1]

## 2. 三种演化尺度

| 尺度 | 允许变化 | 主要评价对象 |
| --- | --- | --- |
| 配置 | 后端、分块、调度参数、合法并行布局 | 支持性、容量、服务指标 |
| Kernel | 分块、布局、融合、加载与线程组织 | 输出语义、shape 覆盖、局部与整体成本 |
| Runtime / Serving | 缓存、调度、通信协同、请求路径 | 状态一致性、取消/终止、并发及尾延迟 |

开放更大尺度前要扩大 oracle 和回归集。只修改一个纯函数所需的证据，与修改请求调度器所需的证据不同。

## 3. 两种基线同时维护

每个候选记录父版本 $x_p$ 和固定比较基线 $x_0$。前者用于衡量当前边际改进，后者用于解释累计效果：

$$
S_{p\to c}=\frac{T(x_p)}{T(x_c)},\qquad
S_{0\to c}=\frac{T(x_0)}{T(x_c)}.
$$

若环境或负载变化，重新测两个基线；不能直接用旧版本在另一机器上的时间组成比值。代码 lineage 描述从哪一版本生成，不代表该路径所有中间候选都有效。

## 4. 组合需要重新评价

对于基线、仅 A、仅 B、A+B 四个完整实现，在同一目标和负载下定义耗时交互量

$$
I_{AB}=T_A+T_B-T_0-T_{AB}.
$$

$I_{AB}>0$ 表示联合节省超过单项节省之和，$I_{AB}<0$ 表示抵消；符号只适用于这个绝对耗时口径。并发改变或测量噪声都可能影响解释。不能用单项加速倍数相乘替代联合测量。

**合成例子：** $T_0=100$、$T_A=90$、$T_B=94$、$T_{AB}=89$ ms，则 $I_{AB}=-5$ ms。两个单项都有效，却共享了部分可消除成本或引入新竞争。下一轮应调查交互，而不是把联合结果写成 $100/(100-10-6)$。

## 5. 候选包的最少内容

- 固定父 SHA、patch/config hash、候选 ID、依赖与冲突列表。
- 优化前冻结的机制说明、预测与适用条件。
- 构建日志、实际执行路径、fallback 和资源上限。
- 独立 oracle 的结果与不可由实现 Agent 修改的评价版本。
- 重复性能数据、真实成本、失败原因与回滚方法。

补丁可以干净应用只说明文本兼容。合并候选还须通过构建、语义和服务回归，且再次核验资源预算。共享内存、编译缓存和环境变量应在实验元数据中记录，避免跨候选污染。

## 6. 跨会话继续优化

会话恢复时读取已确认最优和其证据，而不是读取最后工作目录。新的 Agent 可以质疑旧判断，但应创建新候选与复测记录，不覆盖旧失败原因。后端或环境升级后，相关结果进入待复核状态；重新 profile 决定当前瓶颈。
