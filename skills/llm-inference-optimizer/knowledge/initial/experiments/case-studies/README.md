# 系统案例与跨环境验证

案例把理论、模型和自主优化放到真实推理服务中检验。每个案例固定自己的任务语义与资源条件；跨案例结论必须说明哪些变量发生了变化。

[Qwen / H800 历史案例](https://github.com/Sunhuahai/llm-inference-theory/blob/1b4c5a37763475eb39b31dd083fcad256fc2578e/experiments/case-studies/qwen-h800/README.md)保留既有资料与未知项，不升级其证据状态。以下为新增案例的设计，不代表已经运行。

## 1. 用三条轴组织案例

| 轴 | 起步覆盖 | 扩展后检验什么 |
| --- | --- | --- |
| 模型结构 | 一种可独立验证的稠密架构 | MoE 专家偏斜、混合状态、长上下文的结构迁移 |
| 硬件与并行 | 单设备、明确软件版本 | 不同计算/带宽比、单节点多卡及跨节点通信 |
| 工作负载 | 短输入/长输入、低负载/混合到达 | 缓存复用、长尾输出、突发与尾延迟 |

不要求一次遍历全部组合。先确定一个工作点，再选择一个能挑战当前假设的留出点。只变硬件和同时更换硬件/模型/引擎是不同实验，需分别解释。

## 2. 区分迁移的三种强度

**零额外校准：** 原参数直接预测新环境，检验真实外推能力。**少量校准：** 固定新增微基准预算后适配，检验样本效率。**重新拟合：** 在新环境重新建模，检验方法是否可复用。不能把第三种称为第一种；所有准备成本纳入账本。

同理，经验记忆要区分复用机制解释、复用候选代码与复用测量参数。旧 patch 不能仅因过去通过验证就直接接受；软件版本和 shape 改变后应重新检查。

## 3. 一个案例应交付什么

1. `environment` 和 `workload`：完整版本、资源、到达方式、缓存与质量口径。
2. `hypothesis`：先验瓶颈、候选机制、预期收益及反例。
3. `prediction`：理论边界、模型参数来源、适用域与不确定性。
4. `trials`：代码/配置版本、所有成功与失败、搜索资源消耗。
5. `validation`：冻结 oracle、独立 A/B、留出与复测。
6. `conclusion`：假设是否被支持、适用区域、剩余误差与下一问题。

原始数据体积较大时记录可访问的版本化证据位置及校验和，不提交私密业务 prompt。负结果与收益结果使用同样的描述完整度。通用格式见 [实验模板](../templates/README.md)，服务口径见 [Benchmark 协议](../../docs/benchmark-protocol.md)。
