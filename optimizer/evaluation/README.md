# 自主优化的独立评价

> 状态：实验规范。完整对照设计见 [Agent Benchmark](../../experiments/agent-benchmark/README.md)；已有历史测量口径见[性能协议](../../docs/benchmark-protocol.md)。

## 1. 评价器先于搜索固定

实现 Agent 可以提出修改、诊断失败和请求实验，但不能通过修改 oracle、数据筛选、输出长度或计时方式获得收益。控制器负责锁定评分配置与预算，评价器在干净环境中执行候选，最终结果引用实际运行产物。

独立性是权限和数据流设计，不只是另请一个 LLM 复核。开发评价可反馈给搜索，最终留出集应在候选冻结后使用；对留出集反复调参后，它就已经变成新的开发集。

## 2. 正确性包含什么

| 变更范围 | 必查内容 | 常见漏项 |
| --- | --- | --- |
| 数值 Kernel | dtype、误差容限、NaN/Inf、边界 shape | 只检查一种尺寸或一个随机输入 |
| 随机生成 | 采样算法、分布保证、任务回归 | 把随机样本逐字不同当错误，或把分数接近当分布证明 |
| KV/混合状态 | 前缀键、位置、全部状态的恢复 | 只恢复 KV 而遗漏其他 recurrent state |
| 调度器 | 终止、取消、超时、请求隔离、输出完整性 | 只测成功请求，遗漏排队与丢弃 |
| 分布式实现 | rank 负载、通信、归约语义、失败路径 | 只看平均 rank 耗时 |

固定精度实验不允许重新量化或改变模型来换速度。数值容差须在搜索前按任务语义制定；“低于某个误差值”是否可接受应有 oracle 依据。

## 3. 性能评价分层

局部评价解释机制，服务评价判断价值。KernelBench 同时统计正确性与超过速度阈值的任务比例，适合借鉴局部 Kernel 评价方式；本仓库还需要端到端质量、输入输出分布与服务约束。[1]

正式性能运行应避免重型 profiler 干扰。Nsight Compute 的采集模式与 replay 会影响测量环境，profile 可用于诊断，但不应无条件把其运行时间当作服务正常耗时。[2]

对每个候选，至少分开保存 TTFT、TPOT/ITL、吞吐或 goodput、错误率、峰值内存及搜索成本。目标外的指标仍用作回归约束。单请求变快不能自动推断高并发吞吐变好。

## 4. 重复实验与接受判据

先确定目标、最小有意义改进 $\delta$、约束与最大复测预算。以耗时为例，对配对重复实验定义

$$
d_r=\log T_{0,r}-\log T_{a,r}.
$$

在配对条件与统计方法合适时，可以估计平均 log 加速及其区间。若目标是平均延迟、p99 或 goodput，应使用对应统计量与匹配的抽样单位，不把此式当成通用检验。以独立运行或保留相关性的请求块作为单位，避免把同一批相关请求当独立重复。

接受条件应同时要求：正确性与资源约束通过，性能改善的证据超过预先门槛，独立复测能够重现。没有足够证据则标 `inconclusive`。三次重复可以用于初筛，但不是所有指标尤其尾分位数的充分保证。

反复看结果直到“显著”会改变错误率。初期可预先固定筛选/确认样本量和一次确认时机；需要自适应停止时，应另行采用匹配的序贯方法。搜索很多候选后挑出的最好一次估计有选择偏差，最终必须独立确认。

## 5. 搜索过程的评价

| 指标 | 明确口径 |
| --- | --- |
| 最终确认收益 | 固定预算结束后的独立评价结果 |
| 达到目标成本 | 首次确认达到预设门槛时累计全部成本；未达到记右删失/未达到 |
| 正确候选比例 | 正确候选数除以全部已尝试候选，不删除编译失败 |
| 有效改善比例 | 正确且达到改进门槛的候选数除以全部尝试 |
| 最佳结果随预算曲线 | 只能在评价完成并接受后更新，不使用未来信息 |
| 泛化 | 未参与搜索的 shape、负载、模型或硬件分别报告 |

传统搜索、普通 Agent 与理论引导 Agent 应使用相同任务集合、预算上限、工具权限和基本评价器。额外模型训练、profile 和检索成本应计入对应方法。若搜索空间不同，要分别回答“生成能力”和“排序能力”，避免混在一个结论里。

## 6. 与离线原型的区别

[回放原型](../systems/README.md)的正确性由合成结果表提供，没有真实 oracle、噪声或独立 holdout。它验证失败不晋升、预算不超支、策略不接收未评估结果等控制性质。它不运行本章统计协议，也不能检验真实理论引导效果。
