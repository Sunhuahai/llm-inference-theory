# 每晚反馈与每周归档

## 使用方式

用户每晚可在当前对话贴 [反馈模板](../templates/feedback.md)，也可让实施 Agent 把脱敏结果提交到本周 `feedback/` 与 `results/`。**仓库是持续维护的事实记录**；不能假设定时任务能读到任意新开的私聊或外部 Agent 会话。

反馈最少包括 trick ID、实际修改、baseline→candidate 的 TTFT/TPOT/吞吐、负载条件和异常。没有测到的字段留 `unknown`。即使只有“长输入 TTFT 降了，但并发高时 TPOT 变差”，也先保留现象，补齐判断必须的信息。

## 每次研究更新的顺序

1. 读取远程最新 main、环境、当前周任务与反馈；确认这次真正新增了什么。
2. 把反馈写入 `feedback/YYYY-MM-DD.md`，注明 `user_report` 或对应实测文件。已有日期文件追加带时间的小节，不覆盖先前结论。
3. 检查可比性：模型/精度、GPU 预算、工作负载、输出长度、缓存冷热、测量口径是否一致；有差异则先解释，不直接排名。
4. 更新 trick 状态和 `decisions.md`。记录收益、代价、失败原因与证据路径；保留负结果。
5. 围绕当前瓶颈查一手资料，优先核对源码/已合并 PR/官方文档。提出最多 **2–3 个下一步**，每项写明为什么现在做、要排除哪种解释以及最小实验。
6. 更新 `agent-tasks.md`，交给实施 Agent；不自动替用户运行昂贵实验。

若没有新反馈：明确写“未收到新实测”，只检查相关上游变化，保持当前优先级或解释必要调整。不要每天凑新 trick，也不要复刻已有卡片。对用户只发一次简短反馈邀请或有意义的更新。

## 根据结果选下一步

| 观察 | 下一步研究判断 |
|---|---|
| TTFT 变好，TPOT 变差 | 看 prefill/decode 竞争；固定 offered load 做 token budget 单变量对照 |
| 单请求快，高并发慢 | 看 Graph 覆盖、MTP 验证成本、batch 形状与通信占比 |
| 多轮快，陌生 prompt 不变 | 区分 prefix/state 复用与内核收益；报告冷/暖两条曲线 |
| GPU 利用率低，CPU忙 | 查分词/调度/NUMA/PLE host 取表；不要只增加 batch |
| 平均值改善、p99/错误恶化 | 检查排队、OOM/recompute、cache eviction、长停顿 |
| 稳定提升小于重复波动 | 标 inconclusive；补最少必要对照，或把预算给更强假设 |
| 日志表明功能已默认打开 | 标 baseline-covered，核对是否仍有形状覆盖或参数空间 |
| 接口/后端不支持目标模型 | 标 unsupported，留下版本与报错证据，不强拼旧模型实现 |

此表是研究决策规则，不保证某类现象只有一个原因。

## 周目录规则

- 时区 Asia/Shanghai，ISO 周一至周日；跨年用 ISO week-year。
- 新周第一次维护时创建 `weeks/YYYY-Www/` 和各入口文件，标题写具体起止日期。
- 上周未完成任务写入新周 carry-over 表，链接原 trick，不复制为新发现。原周证据保留；后续状态在新周决策中链接。
- 每周总结列出有效/负结果/未决及下周最多三项优先级。无实验就明确无实验，不编造周报收益。
