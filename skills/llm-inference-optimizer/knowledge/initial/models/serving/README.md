# 服务模型：从一次执行到请求分布

> 状态：模型设计与 `derived` 关系，2026-11-25。当前没有完整在线服务模拟器。

## 1. 工作负载必须保留哪些信息

一个“平均输入 4K、输出 256”的描述不足以预测服务。长请求可以与高峰到达相关，共享前缀也会与会话时间相关；这些关联影响排队、状态容量和缓存价值。

| 工作负载字段 | 用途 | 不能替代它的量 |
| --- | --- | --- |
| 计划到达和实际发送时间 | 区分服务队列与客户端积压 | 名义 RPS |
| 输入/实际输出长度联合分布 | Prefill 工作、Decode 步数及驻留时间 | 两个独立均值 |
| 前缀键、命中边界、复用间隔 | 缓存访问与驱逐 | 总命中率 |
| 任务类型、EOS/采样、质量要求 | 固定语义与有效产出 | 强制相同输出长度 |
| 路由与副本、模型/适配器版本 | 缓存局部性和资源争用 | 集群总卡数 |
| 到达模式与时间段 | 突发、周期性、非平稳变化 | 固定并发压测 |

合成工作负载适合研究变量关系，必须标为 `synthetic`；真实 trace 可用脱敏键和长度保留必要结构。训练/校准/测试 trace 按会话或时间块拆分，不能让同一共享前缀出现在两侧而声称完全独立。

## 2. 服务时间由状态决定

动态 batch 下，第 $t$ 步的时间不是常数：

$$
\tau_t=g(B_t,N_{P,t},\{\ell_{i,t}\},\text{route}_t,\text{state}_t,\text{backend}).
$$

$B_t$ 是 Decode 活跃数，$N_{P,t}$ 是该步 Prefill token 数。调度、容量和请求完成会改变后续输入。只有建立相应事件过程后，才能生成每请求首 token 和末 token 时间。

对请求 $i$，按统一观测点：

$$
TTFT_i=t_{i,1}-a_i,\quad TPOT_i=\frac{t_{i,n_i}-t_{i,1}}{n_i-1}\;(n_i>1).
$$

分位数从逐请求时间线统计；不能把 Prefill p95 与排队 p95 相加。输出吞吐、请求吞吐和同时满足约定约束的 goodput 分开报告，公式与边界见[服务理论](../../theory/serving/README.md)。

## 3. 相同均值可以有不同结果

合成对照 A 的每请求输入长度都为 4K；B 为一半 1K、一半 7K。二者平均长度相同，但若注意力成本含二次项，则 B 的平均二次成本相对 A 为：

$$
\frac{(1^2+7^2)/2}{4^2}=\frac{25}{16}=1.5625.
$$

这只比较理想二次项，不是完整 Prefill 加速比；线性工作、因果位置对、引擎切分和缓存会改变端到端差异。它说明用平均长度替换分布会丢失决定性能的信息。

## 4. 预测目标需明确

低负载 TTFT/TPOT、固定到达负载下的完成吞吐、饱和容量、满足 SLO 的最大接纳率，是不同目标。稳定且无丢失时，提高服务能力不会让到达率不变的系统凭空完成更多请求。近饱和时，改善可能主要表现为队列缩短和超时减少。

对 P/D 分离，要把 Prefill、Decode 和状态传输统一折算到同一请求分布下的请求容量，再考虑阶段队列与路由；不能把 prefill tokens/s 和 decode tokens/s 直接取最小值。[Vidur][vidur]给出了 profile 与服务仿真结合的公开方法，本仓库借鉴这种分层思想，不假定其支持所有目标架构。

## 5. 可证伪预测与下一次实验

先固定三个代表性负载：低负载延迟、靠近容量的开环负载、长度混合的留出负载。模型应同时解释改动收益和至少一个失效区域；只在单一并发下吻合不能证明普适性。对无法辨识的调度/干扰项，输出 `unknown` 并请求针对性 trace。
