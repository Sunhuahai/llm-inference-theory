# 服务仿真：离散事件模型的设计与验证

> 状态：设计说明，2026-11-25。本目录没有伪装为已实现的通用模拟器；现有可运行部分是 [固定图解析参考](https://github.com/Sunhuahai/llm-inference-theory/blob/1b4c5a37763475eb39b31dd083fcad256fc2578e/models/analytic/README.md)和[按序缓存回放](https://github.com/Sunhuahai/llm-inference-theory/blob/1b4c5a37763475eb39b31dd083fcad256fc2578e/models/predictor/CACHE_CONTEXT_SCHEMA.md)。

## 1. 为什么需要事件

改变 batch 或缓存后，不仅单步时间改变，请求何时进入、何时退出、状态何时分配也会改变。仿真应先生成这些事件，再计算指标，不能用一个经验吞吐倍率统一缩放全部时间。

建议状态包含：等待队列、活跃请求、每请求输入/输出进度、KV/其他状态位置、每资源忙闲时刻、缓存索引与引用计数、P/D 阶段及传输队列。事件包含到达、准入、Prefill 完成、Decode 提交、传输完成、取消/超时、释放和驱逐。

## 2. 一步状态转移

在时刻 $t$，调度策略 $\pi$ 从状态 $s_t$ 选定动作 $a_t$。执行模型提供阶段时长和资源使用，事件引擎更新：

$$
(s_{t+\Delta},\mathcal E_{t+\Delta})=\Phi(s_t,a_t,\widehat\tau,\text{capacity},\text{arrivals}).
$$

这只是接口定义，不对真实系统的转移正确性作保证。事件时间相同的处理顺序必须固定并记录，例如先完成与释放、再接受新请求、最后调度。若实引擎使用不同规则，应按其语义调整；不能把方便实现的规则当作实际默认。

## 3. 最小实现顺序

| 阶段 | 新增能力 | 必须满足的验证 |
| --- | --- | --- |
| 静态请求 | 单请求、固定阶段、无争用 | 手算 TTFT/E2E，确保首 token 不重复计时 |
| 到达与队列 | 固定服务、开环请求 | 工作守恒、完成/失败守恒、已知简单队列极限 |
| 动态批处理 | token budget、异长进度、生命周期 | 无重复提交，容量不越界，输出数一致 |
| 状态共享 | prefix 命中、分配/驱逐/恢复 | 引用数、键语义、冷/热 trace 回放 |
| 多资源 | P/D、网络、路由、互联争用 | 阶段守恒、传输字节、每 rank 瓶颈 |

每一步都保留上一阶段可手算特例。提前加入复杂调度而没有守恒测试，容易把实现错误解释成“非线性收益”。

## 4. 一个反例说明必要性

合成例：两个请求都在 0 ms 到达，服务资源每次只处理一个请求，每个请求独占 5 ms。如果误当两个独立执行图并行，则两者都在 5 ms 完成；实际固定 FCFS 排程分别在 5 ms 与 10 ms 完成。相同单请求模型可以得到错误的队列结果。

动态 batch 会允许不同的共享方式，但它必须由校准过的批成本和明确调度规则产生。不能把“独占排程不成立”当作“全部请求可以免费并发”的依据。

## 5. 模拟器本身也要校准

采用三层误差归因：算子时长误差、事件/调度误差、工作负载输入误差。先用实测阶段时长驱动事件模型；若仍无法重现服务，应修正调度和状态语义。然后才用算子预测替代实测时长，隔离新增误差。

留出负载应覆盖长度、并发、到达突发和缓存冷热变化。报告分层误差与失效区域，不能只给总体平均误差。仿真输出的 p99 是“在模型与输入假设下的 p99”，不是 GPU 实测证据。

[Vidur 论文][vidur]展示了结合算子 profiling、预测和服务仿真的路线；具体算法和公开误差只对其原实验成立。此处事件契约与分阶段实施是本仓库的研究设计。
